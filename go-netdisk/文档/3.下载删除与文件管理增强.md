# 第三步实现文档：下载、删除、重命名、移动与容量管理

## 1. 目标

前两步你已经完成了两条关键链路：

1. `启动服务 -> 注册登录 -> 返回 JWT`
2. `JWT 鉴权 -> 当前用户 -> 新建目录 -> 上传文件 -> 文件列表`

第三步不要急着做分享链接、在线预览、图片缩略图、分片上传。

这一步只做“基础文件管理能力增强”：

1. 文件下载接口
2. 文件/目录删除接口
3. 文件/目录重命名接口
4. 文件/目录移动接口
5. 列表分页与排序
6. 用户容量统计

只要这一步完成，你的网盘后端就不再只是“能放文件”，而是具备基本可持续使用能力。

## 2. 这一步为什么重要

第二步解决的是“把文件放进去、把列表查出来”。

第三步解决的是“文件进去之后怎么管理”。

一个网盘最基础的用户行为，通常是下面这条链：

`上传 -> 查看 -> 下载 -> 重命名 -> 移动 -> 删除`

如果没有第三步，这个系统仍然更像一个“临时上传盒子”，而不是可用的文件系统接口。

## 3. 这一步最终要做出的效果

你做完后，应该能完成下面这些操作：

1. 下载已上传的文件
2. 删除一个文件
3. 删除一个空目录，或者递归删除目录
4. 修改文件名或目录名
5. 把文件移动到另一个目录
6. 按页查看目录列表
7. 查看当前用户已用空间

到这里为止，你的项目就具备了最核心的一组网盘操作能力。

## 5. 建议先实现的功能顺序

这一步建议按下面顺序做：

1. 文件下载接口
2. 删除文件/目录接口
3. 重命名接口
4. 移动接口
5. 文件列表分页和排序
6. 用户容量统计

顺序原因很明确：

- 下载最独立，改动最小
- 删除会涉及数据库和磁盘一致性
- 重命名和移动会涉及路径更新
- 分页排序和容量统计是“增强项”，放在后面更稳

## 6. `Matter` 模型第三步建议补哪些字段

如果你第二步的 `Matter` 还是极简版，第三步建议补充这些字段中的一部分：

```go
type Matter struct {
    ID        uint      `gorm:"primaryKey" json:"id"`
    UUID      string    `gorm:"type:varchar(36);uniqueIndex;not null" json:"uuid"`
    UserID    uint      `gorm:"index;not null" json:"userId"`
    PUUID     string    `gorm:"type:varchar(36);index;not null" json:"puuid"`
    Name      string    `gorm:"type:varchar(255);not null" json:"name"`
    Path      string    `gorm:"type:varchar(1024);not null" json:"path"`
    FileType  string    `gorm:"type:varchar(32)" json:"fileType"`
    Size      int64     `gorm:"not null;default:0" json:"size"`
    IsDir     bool      `gorm:"not null;default:false" json:"isDir"`
    Times     uint32    `gorm:"not null;default:0" json:"times"`
    CreatedAt time.Time `json:"createdAt"`
    UpdatedAt time.Time `json:"updatedAt"`
}
```

建议理解：

- `Times`：下载次数，可选，但如果你要做下载统计会比较方便
- `UpdatedAt`：后续重命名、移动时会更新

如果你当前不想加 `Times`，完全可以先不加。第三步真正必须的是“路径和父目录关系能稳定维护”。

## 7. `User` 模型第三步建议补哪些字段

如果你准备做容量统计，建议在 `User` 模型里增加：

```go
type User struct {
    ID             uint      `gorm:"primaryKey" json:"id"`
    UUID           string    `gorm:"type:varchar(36);uniqueIndex;not null" json:"uuid"`
    Username       string    `gorm:"type:varchar(64);uniqueIndex;not null" json:"username"`
    Password       string    `gorm:"type:varchar(255);not null" json:"-"`
    TotalSize      int64     `gorm:"not null;default:0" json:"totalSize"`
    TotalSizeLimit int64     `gorm:"not null;default:-1" json:"totalSizeLimit"`
    CreatedAt      time.Time `json:"createdAt"`
    UpdatedAt      time.Time `json:"updatedAt"`
}
```

建议理解：

- `TotalSize`：当前用户已经使用了多少空间
- `TotalSizeLimit`：允许使用的最大空间，`-1` 可以表示不限

第三步不一定要马上做复杂容量策略，但提前把字段留出来会更顺。

## 9. 文件下载接口应该怎么设计

接口：

```text
GET /api/matter/:uuid/download
```

请求头：

```text
Authorization: Bearer <token>
```

处理逻辑：

1. 认证用户
2. 根据 `uuid` 查询文件记录
3. 校验这个文件属于当前用户
4. 校验它不是目录
5. 根据数据库里的相对路径拼出真实磁盘路径
6. 返回附件下载
7. 可选：下载次数加一

### 为什么下载用 `uuid` 不用文件名

因为文件名不是稳定唯一标识：

- 同名文件可能存在
- 文件名可能被重命名
- 文件名里可能有特殊字符

所以下载接口建议始终基于 `uuid`。

### 返回方式建议

Gin 里可以用：

```go
c.FileAttachment(realPath, matter.Name)
```

这样浏览器会按附件下载，而不是直接把文件内容当文本返回。

## 10. 删除接口应该怎么设计

接口：

```text
POST /api/matter/delete
```

请求体：

```json
{
  "uuid": "xxx"
}
```

处理逻辑：

1. 认证用户
2. 查目标记录
3. 校验归属权
4. 判断是文件还是目录
5. 删除磁盘文件或目录
6. 删除数据库记录
7. 更新用户已用空间

### 第三步删除功能最关键的问题

不是“怎么删”，而是“磁盘和数据库怎么保持一致”。

建议原则：

1. 先查清楚目标记录
2. 确认真实路径一定落在 `storage.root` 下面
3. 删除磁盘文件
4. 删除数据库记录
5. 回收用户已用空间

### 目录删除怎么处理

第三步你有两个选择：

1. 只允许删除空目录
2. 允许递归删除目录

更建议先做第 1 种，因为更安全、更容易验证。

如果你要做递归删除，必须注意两件事：

- 子节点数据库记录也要一起删
- 目录下所有文件大小都要正确扣减

## 11. 重命名接口应该怎么设计

接口：

```text
POST /api/matter/rename
```

请求体：

```json
{
  "uuid": "xxx",
  "name": "new-name.txt"
}
```

处理逻辑：

1. 认证用户
2. 查询目标文件或目录
3. 校验归属权
4. 检查同级目录下是否重名
5. 修改真实磁盘名称
6. 更新当前记录的 `name` 和 `path`
7. 如果目标是目录，递归更新所有子文件路径

### 为什么重命名目录会更复杂

因为目录的 `path` 一旦变了，下面所有子文件和子目录的 `path` 前缀都要跟着变。

例如：

```text
/1/docs
/1/docs/a.txt
/1/docs/sub/b.txt
```

如果把 `docs` 改成 `work`，那就要全部更新为：

```text
/1/work
/1/work/a.txt
/1/work/sub/b.txt
```

所以第三步更稳妥的做法是：

1. 先实现文件重命名
2. 再实现目录重命名

不要一开始就把目录重命名做得过重。

## 12. 移动接口应该怎么设计

接口：

```text
POST /api/matter/move
```

请求体：

```json
{
  "uuid": "file-uuid",
  "target_puuid": "dir-uuid"
}
```

处理逻辑：

1. 认证用户
2. 查源文件或目录
3. 查目标目录
4. 校验二者都属于当前用户
5. 校验目标确实是目录
6. 校验目标目录下没有重名
7. 修改磁盘位置
8. 更新数据库里的 `puuid` 和 `path`
9. 如果移动的是目录，递归更新所有子路径

### 移动接口的高风险点

第三步最容易出 bug 的地方就是移动目录。

建议最小实现路线：

1. 先只支持文件移动
2. 再支持空目录移动
3. 最后再支持非空目录移动

这样比一次把全部情况堆进去更可靠。

## 13. 文件列表第三步应该增强什么

第二步的列表接口只要求“能查出来”。

第三步建议补两类能力：

1. 分页
2. 排序

接口建议：

```text
GET /api/matter/list?puuid=root&page=1&page_size=20&order=name&direction=asc
```

建议支持的参数：

- `puuid`：父目录 UUID
- `page`：页码
- `page_size`：每页数量
- `order`：排序字段
- `direction`：升序或降序

建议先支持的排序字段：

- `name`
- `created_at`
- `updated_at`
- `size`

### 列表排序建议

前端体验通常会希望“目录在前，文件在后”。

所以即使支持普通排序，内部也可以保留一个优先规则：

1. 目录优先
2. 再按用户指定字段排序

## 14. 容量统计应该做到什么程度

第三步不建议一上来做复杂配额系统。

建议只做这 3 件事：

1. 用户上传文件时增加 `TotalSize`
2. 用户删除文件时减少 `TotalSize`
3. 提供一个接口查询当前已用空间和总限额

接口：

```text
GET /api/user/storage
```

返回示例：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "totalSize": 1048576,
    "totalSizeLimit": 1073741824
  }
}
```

### 上传前是否校验容量

建议要做。

上传前先判断：

```text
current_total_size + upload_file_size <= total_size_limit
```

如果超限，直接返回错误。

这会让你的系统从第三步开始就具备最基本的资源约束能力。

## 15. 路径更新是第三步的核心难点

第三步真正复杂的不是增删改查接口本身，而是“路径一致性”。

你要同时维护两个世界：

1. 磁盘上的真实目录结构
2. 数据库里的 `path` 和 `puuid`

只要重命名、移动目录，这两个世界就必须同步。

建议原则：

- 数据库里存相对路径
- 所有路径拼接都从统一函数生成
- 不要到处手写字符串拼接

例如建议封装：

1. 根据 `puuid` 算父目录相对路径
2. 根据 `name` 生成当前节点相对路径
3. 根据相对路径拼接真实磁盘路径

这样后面改动会少很多。

## 16. 删除和移动要特别注意安全

第三步开始会触碰真正的文件删除和移动，所以一定要加基本安全约束。

至少要做这些检查：

1. 当前记录必须属于当前用户
2. 真实路径必须在 `storage.root` 目录下
3. 不能允许用户伪造路径删除任意系统文件
4. 目录不能移动到自己的子目录里

### 为什么“目录移动到自己的子目录里”危险

比如把：

```text
/1/docs
```

移动到：

```text
/1/docs/sub
```

这是非法的，会造成逻辑循环。

所以移动目录时要检查目标目录是否位于当前目录子树中。

## 17. 推荐的分层职责

第三步依然要保持分层，不然很快会乱。

### handler

负责：

- 收参数
- 返回 JSON
- 不直接操作磁盘

### service

负责：

- 下载前权限校验
- 删除逻辑
- 重命名逻辑
- 移动逻辑
- 容量统计逻辑

### model

负责：

- `User`
- `Matter`
- 基础查询方法

### middleware

负责：

- 认证用户身份

### filesystem 操作建议

如果第三步逻辑越来越多，可以在 `service` 里抽一些小函数，例如：

- `buildRealPath(...)`
- `renameMatterPath(...)`
- `moveMatterPath(...)`
- `collectDirectorySize(...)`

不一定现在单独拆包，但至少不要把所有 `os.Rename`、`os.RemoveAll`、路径替换逻辑都堆在 handler 里。

## 19. 这一步的验收标准

你可以按这个清单自测：

- [ ] 当前用户可以下载自己上传的文件
- [ ] 用户不能下载别人的文件
- [ ] 删除单个文件后，磁盘和数据库记录都消失
- [ ] 删除文件后，用户已用空间会减少
- [ ] 文件重命名后，列表里能看到新名称
- [ ] 文件移动后，在新目录里能查到
- [ ] 目录不能被移动到自己的子目录下
- [ ] 列表接口支持分页参数
- [ ] 列表接口支持排序参数
- [ ] `/api/user/storage` 能返回正确容量信息

只要这 10 条通过，你的第三步就算完成了。
