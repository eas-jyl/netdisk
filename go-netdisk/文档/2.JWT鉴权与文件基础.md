# 第二步实现文档：JWT 鉴权、当前用户、文件基础能力

## 1. 目标

第一步你已经完成了：

1. 服务启动
2. 配置加载
3. MySQL 连接
4. `users` 表自动迁移
5. 注册接口
6. 登录接口
7. JWT Token 返回

第二步不要急着做复杂分享、权限细化、在线预览。

这一步只做“登录后的最小文件能力闭环”：

1. 增加 JWT 鉴权中间件
2. 增加当前用户信息接口
3. 增加文件目录模型 `Matter`
4. 支持新建文件夹
5. 支持上传文件
6. 支持文件列表查询

只要这一步完成，你的项目就从“能登录”进入“能作为网盘基础使用”的阶段。

## 2. 这一步为什么重要

第一步解决的是“用户是谁”。

第二步解决的是“用户登录后能操作什么”。

网盘后续的大部分功能，本质上都依赖下面这条链：

`携带 Token -> 服务端识别用户 -> 找到该用户的目录/文件 -> 返回列表或执行操作`

所以第二步的本质，是把“身份识别”真正接到“文件系统能力”上。

## 3. 这一步最终要做出的效果

你做完后，应该能完成下面这些操作：

1. 登录拿到 Token
2. 携带 Token 请求受保护接口
3. 获取当前登录用户信息
4. 创建一个文件夹
5. 上传一个文件
6. 查看某个目录下的文件列表

到这里为止，后面做下载、删除、移动、分享，都会顺很多。

## 5. 建议先实现的功能顺序

不要并行乱写，按这个顺序最稳：

1. 实现 JWT 中间件
2. 给受保护路由挂中间件
3. 实现当前用户信息接口
4. 设计 `Matter` 模型
5. 启动时自动迁移 `matters` 表
6. 设计上传根目录配置
7. 实现新建文件夹接口
8. 实现文件上传接口
9. 实现文件列表接口

这个顺序的好处是：

- 前 3 步先打通“登录后访问”
- 后 6 步再做“登录后操作文件”

## 6. 配置文件建议新增什么

建议在 `config/dev.yaml` 里新增一段上传目录配置：

```yaml
app:
  name: go-netdisk
  port: 8080

mysql:
  host: 127.0.0.1
  port: 3306
  user: root
  password: root
  dbname: go_netdisk

jwt:
  secret: your-secret-key
  expire_hours: 24

storage:
  root: ./storage/upload
```

说明：

- `storage.root` 表示文件最终保存到哪里
- 第二步先保存到本地目录，不要一上来接 OSS、MinIO、S3

## 7. JWT 中间件应该做什么

第一步你已经能生成 Token，但还没有真正“保护接口”。

第二步的 JWT 中间件建议做到这些：

1. 从请求头读取 Token
2. 校验 Token 是否合法
3. 校验 Token 是否过期
4. 从 Token 中拿出 `user_id`、`username`
5. 把用户信息写入 `gin.Context`
6. 非法 Token 返回 `401`

推荐请求头格式：

```text
Authorization: Bearer <token>
```

中间件的职责不要扩散：

- 它只负责“认证”
- 不负责文件业务
- 不负责数据库写操作

## 8. 当前用户接口应该怎么设计

接口：

```text
GET /api/user/me
```

请求头：

```text
Authorization: Bearer <token>
```

处理逻辑：

1. 经过 JWT 中间件
2. 从上下文里拿出用户 ID 或用户名
3. 查询数据库
4. 返回当前用户信息

返回示例：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "id": 1,
    "uuid": "xxx",
    "username": "admin"
  }
}
```

这个接口的意义很大：

- 用来验证 Token 是否真的可用
- 用来验证中间件有没有把用户信息传下来
- 后续很多页面初始化都靠它

## 9. `Matter` 模型第一版怎么设计

第二步不要一开始把文件模型设计得过重。

建议先保留最关键字段：

```go
type Matter struct {
    ID        uint      `gorm:"primaryKey" json:"id"`
    UUID      string    `gorm:"type:varchar(36);uniqueIndex;not null" json:"uuid"`
    UserID    uint      `gorm:"index;not null" json:"userId"`
    PUUID     string    `gorm:"type:varchar(36);index;not null" json:"puuid"`
    Name      string    `gorm:"type:varchar(255);not null" json:"name"`
    Path      string    `gorm:"type:varchar(1024);not null" json:"path"`
    FileType  string    `gorm:"type:varchar(32)" json:"fileType"`
    Size      int64     `gorm:"not null;default:0" json:"size"`
    IsDir     bool      `gorm:"not null;default:false" json:"isDir"`
    CreatedAt time.Time `json:"createdAt"`
    UpdatedAt time.Time `json:"updatedAt"`
}
```

建议理解如下：

- `UserID`：这个文件属于哪个用户
- `PUUID`：父目录 UUID
- `Name`：文件名或目录名
- `Path`：文件在磁盘中的相对路径
- `FileType`：简单文件类型，比如 `image`、`video`、`text`
- `Size`：文件大小
- `IsDir`：是否目录

### 根目录怎么处理

第二步建议提前约定一个根目录标识，比如：

```text
root
```

也就是：

- 用户顶层目录的 `PUUID` 可以固定为 `root`
- 查询列表时，如果传入 `puuid=root`，就表示查看根目录内容

这样可以避免一开始就陷入复杂目录树设计。

## 10. 启动时应该自动迁移哪些表

在第一步的基础上，第二步启动时建议迁移：

1. `users`
2. `matters`

也就是数据库初始化里应该变成：

```go
db.AutoMigrate(&model.User{}, &model.Matter{})
```

这样你每次启动都能自动把第二步用到的表建起来。

## 11. 路由第二版建议

第二步建议保留第一步的接口，并新增这些：

```text
GET  /ping
POST /api/account/register
POST /api/account/login

GET  /api/user/me

GET  /api/matter/list
POST /api/matter/directory

```

建议分成两组：

1. 公开路由

2. 受保护路由

第二组统一挂 JWT 中间件。

## 12. 新建文件夹接口应该怎么设计

接口：

```text
POST /api/matter/directory
```

请求头：

```text
Authorization: Bearer <token>
```

请求体：

```json
{
  "puuid": "root",
  "name": "docs"
}
```

处理逻辑：

1. 认证用户
2. 校验目录名不能为空
3. 查父目录是否存在
4. 检查同级目录下是否重名
5. 在磁盘上创建真实目录
6. 在 `matters` 表写入目录记录
7. 返回目录信息

返回示例：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "uuid": "xxx",
    "puuid": "root",
    "name": "docs",
    "path": "/1/docs",
    "isDir": true
  }
}
```

### 第二步建议简化的点

先不要做：

- 多级目录权限检查
- 目录递归大小统计
- 复杂重名策略

只要同级不重名、目录能创建成功，就够了。

## 13. 文件上传接口应该怎么设计

接口：

```text
POST /api/matter/upload
```

请求类型：

```text
multipart/form-data
```

表单字段建议：

- `file`：上传文件
- `puuid`：父目录 UUID，默认可传 `root`

处理逻辑：

1. 认证用户
2. 读取上传文件
3. 根据 `puuid` 找到父目录
4. 生成实际保存路径
5. 保存文件到本地磁盘
6. 写入 `matters` 表
7. 返回文件信息

返回示例：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "uuid": "xxx",
    "puuid": "root",
    "name": "a.txt",
    "path": "/1/a.txt",
    "size": 123,
    "isDir": false
  }
}
```

### 第二步上传功能先做到什么程度

第二步只要求：

1. 单文件上传
2. 本地磁盘存储
3. 数据库有记录
4. 同目录下能在列表里看到

先不要做：

- 分片上传
- 秒传
- 断点续传
- MD5 去重
- 大文件优化

## 14. 文件列表接口应该怎么设计

接口：

```text
GET /api/matter/list?puuid=root
```

请求头：

```text
Authorization: Bearer <token>
```

处理逻辑：

1. 认证用户
2. 读取查询参数 `puuid`
3. 按 `user_id + puuid` 查询该目录下的文件
4. 默认按目录在前、创建时间倒序或名称排序
5. 返回当前目录列表

返回示例：

```json
{
  "code": 0,
  "message": "ok",
  "data": [
    {
      "uuid": "dir-1",
      "name": "docs",
      "isDir": true
    },
    {
      "uuid": "file-1",
      "name": "a.txt",
      "isDir": false,
      "size": 123
    }
  ]
}
```

第二步先不强求分页。

如果你当前目录下文件量不会太大，先把“能查出来”做稳，比一开始就加复杂筛选更重要。

## 15. 路径设计建议

第二步最容易把自己绕晕的，就是“数据库路径”和“真实磁盘路径”的关系。

建议分清两种路径：

1. 相对业务路径
   比如：

```text
/1/docs/a.txt
```

这个适合存数据库。

2. 真实磁盘路径
   比如：

```text
./storage/upload/1/docs/a.txt
```

这个适合真正保存文件。

建议做法：

- 数据库里保存相对路径
- 保存文件时再拼接 `storage.root`

这样后面迁移存储位置时更容易调整。

## 16. 推荐的分层职责

为了第三步继续扩展，第二步仍然建议保持清晰分层。

### middleware

负责：

- 提取 Token
- 校验 Token
- 向上下文写入登录用户信息

### handler

负责：

- 接收 HTTP 请求
- 校验基础参数
- 调用 service
- 返回 JSON

不要在这里直接写文件系统细节和数据库细节。

### service

负责：

- JWT 解析后的业务处理
- 当前用户查询
- 目录创建
- 文件上传
- 文件列表查询

### model

负责：

- `User`
- `Matter`

### db

负责：

- 数据库连接
- 自动迁移

### 第 5 步：写上传接口

## 18. 这一步的验收标准

你可以按这个清单自测：

- [ ] 不带 Token 访问 `/api/user/me` 会返回 `401`
- [ ] 带合法 Token 访问 `/api/user/me` 成功
- [ ] 启动后数据库自动生成 `matters` 表
- [ ] 创建目录接口成功
- [ ] 磁盘上能看到实际创建的目录
- [ ] 上传文件接口成功
- [ ] 磁盘上能看到上传后的文件
- [ ] `matters` 表里有目录和文件记录
- [ ] 文件列表接口能查出当前目录内容
- [ ] 不同用户的数据不会串目录

只要这 10 条都通过，你的第二步就算完成了。

## 19. 这一步不要急着做的事情

下面这些先别做，不然第二步很容易失控：

- 下载接口
- 删除文件/目录
- 文件重命名
- 文件移动
- 文件分享
- 图片预览
- 视频转码
- 缩略图
- 空间统计
- 分片上传

第二步的关键是先把：

`JWT 鉴权 -> 用户识别 -> 目录记录 -> 本地上传 -> 列表查询`

这条链打穿。

## 20. 和原项目的对应关系

你现在第二步做的是原项目里的“认证后基础文件能力”，大致对应这些位置：

- `example/pkg/middlewares/jwt.go`
- `example/pkg/db/models/matter.go`
- `example/pkg/services/user/handler.go`
- `example/pkg/services/matter/handler.go`

注意：

原项目里的 `Matter` 结构和接口会更复杂。

你第二步不需要一次复刻完整：

- 可以先不做下载次数
- 可以先不做隐私控制
- 可以先不做复杂过滤分页
- 可以先不做权限角色细化

先做最小可运行版本最重要。

## 21. 做完第二步之后，第三步建议做什么

第三步建议实现：

1. 文件下载接口
2. 删除文件/目录接口
3. 重命名接口
4. 移动文件接口
5. 基础分页和排序
6. 用户容量统计

也就是从“基础可用”进入“可持续使用”的阶段。

## 22. 最终建议

第二步不要追求大而全。

真正关键的是把下面这条链稳定跑通：

`登录拿 Token -> 中间件识别用户 -> 创建目录 -> 上传文件 -> 查询列表`

只要这条链通了，你的网盘后端骨架就已经基本成型。
